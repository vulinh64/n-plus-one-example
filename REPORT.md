## Log Analysis

### No transaction

The endpoint first selects the authors, then the repository transaction closes. The mapper subsequently accesses `Author.books` while the entities are detached, causing:

```text
LazyInitializationException: failed to lazily initialize a collection of role:
com.vulinh.data.entity.Author.books: could not initialize proxy - no Session
```

This is why `/author/no-transaction` returns HTTP 500.

### Transactional lazy loading

`/author/transactional` keeps the Hibernate session open while mapping. It succeeds, but generates:

- 1 query for all authors
- 5 individual book queries, one for each author

Total: 6 SELECT queries. This is the standard `N+1` query problem.

### Entity graph and join fetch

Both author fetch strategies load authors and books in one SQL query. They remove N+1, but both log:

```text
HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory
```

Hibernate cannot safely apply database pagination to a collection fetch join, so it retrieves the joined result and paginates in memory. This can cause high memory use and slow responses on large datasets.

### Batch fetch

`/customer/batch-fetch` uses `@BatchSize(size = 5)`:

- 1 query for 10 customers
- 2 order queries, each loading orders for 5 customer IDs

Total: 3 SELECT queries. This is much better than N+1 while preserving the lazy association.

### Explicit two-query loading

`/customer/diy` performs:

- 1 paginated customer query
- 1 order query using all returned customer IDs

Total: 2 SELECT queries. This has predictable query behavior and preserves database pagination for the parent records.

### Multiple lazy collections

`/product/multiple-collection-n-plus-one` performs:

- 1 query for products
- 3 category queries, one per product
- 3 available-store queries, one per product

Total: 7 SELECT queries, following `1 + 2N`.

The multiple-collection entity graph reduces this to one SQL query, but it also logs the in-memory pagination warning. Additionally, joining both collections creates a Cartesian multiplication of category and store rows before Hibernate deduplicates the entities. With the current data, the database returns 36 joined rows for only 3 products.

### Multiple Bag Fetch Limitation

As an additional experiment, both `Product.categories` and `Product.availableStores` were changed from `Set` to `List`. Calling:

```text
GET /product/multiple-collection-entity-graph?page=0&size=20
```

then returned HTTP 500 with:

```text
MultipleBagFetchException: cannot simultaneously fetch multiple bags:
[com.vulinh.data.entity.Product.availableStores, com.vulinh.data.entity.Product.categories]
```

Hibernate treats unordered `List` associations as bags. It cannot simultaneously fetch-join multiple bags because the Cartesian result does not contain enough information to reliably reconstruct both collections without introducing duplicate elements.

The failure occurred while Hibernate was constructing the query. No SELECT query was executed, and the transaction was rolled back. The existing `HHH90003004` in-memory pagination warning was also logged before the exception.

Using `Set` avoids `MultipleBagFetchException` because Hibernate can deduplicate collection elements. However, it does not remove the Cartesian row multiplication or in-memory pagination risks described above.

Two mixed collection-type configurations were also tested:

| `Product.categories` | `Product.availableStores` | HTTP status | SELECT queries | Result           |
|----------------------|---------------------------|------------:|---------------:|------------------|
| `Set`                | `List`                    |         200 |              1 | Successful fetch |
| `List`               | `Set`                     |         200 |              1 | Successful fetch |

Both configurations returned the expected three products without duplicate collection elements. Hibernate permits fetching one bag alongside a `Set`; the exception occurs only when it must simultaneously fetch more than one bag.

Reversing which association was the `List` did not otherwise change the behavior. Both mixed configurations still:

- fetched both collections with one joined SELECT query;
- logged `HHH90003004` because pagination was applied in memory;
- produced Cartesian row multiplication before Hibernate reconstructed the collections.

## Small Page Pagination Experiment

All endpoints were called again with:

```text
page=0&size=3
```

This page size is smaller than the number of authors and customers. It exposes behavior that was hidden when `size=20` covered the complete result set.

|---------------------------------------------|------------:|---------------:|--------------------------:|----------------------------------------------------------------------------|

| `/author/transactional`                     |         200 |              5 |                     3 / 5 | Database pagination; lazy query for each returned author                   |
| `/author/entity-graph`                      |         200 |              2 |                     3 / 5 | Joined collection loaded before in-memory pagination                       |
| `/author/join-fetch` with `distinct`        |         200 |              2 |                     3 / 5 | Joined collection loaded before in-memory pagination                       |
| `/customer/batch-fetch`                     |         200 |              3 |                    3 / 10 | Database pagination; one batch query for the returned customers            |
| `/customer/diy`                             |         200 |              3 |                    3 / 10 | Database pagination; one explicit query for the returned customers' orders |
| `/product/multiple-collection-n-plus-one`   |         200 |              8 |                     3 / 3 | Database pagination; two lazy collection queries per returned product      |
| `/product/multiple-collection-entity-graph` |         200 |              2 |                     3 / 3 | Joined collections loaded before in-memory pagination                      |

### Count Query Behavior

When the returned content fills the requested page, Spring Data cannot infer that the page is the last one. It executes a count query to calculate `totalElements` and `totalPages`.

The original author join-fetch query did not use `distinct`. Its generated count query counted joined book rows:

```sql
select count(a1_0.id)
from author a1_0
left join book b1_0 on a1_0.id = b1_0.author_id
```

This incorrectly reported `totalElements=15` and `totalPages=5`, even though there are only 5 authors.

After adding `distinct` to the JPQL join-fetch query, Hibernate generated:

```sql
select count(distinct a1_0.id)
from author a1_0
left join book b1_0 on a1_0.id = b1_0.author_id
```

The endpoint then correctly reported `totalElements=5` and `totalPages=2`.

### Database and In-Memory Pagination

Smaller page sizes reduce database work only for strategies that apply `offset` and `limit` to the parent query:

- plain lazy loading;
- transactional N+1 loading;
- batch fetching;
- explicit two-query loading.

For these strategies, association queries run only for the parents contained in the requested page. Their general query-count patterns are:

| Strategy                     | Query-count pattern                                                |
|------------------------------|--------------------------------------------------------------------|
| Transactional N+1            | parent query + count query + one child query per page element      |
| Batch fetch                  | parent query + count query + child batch queries for page elements |
| Explicit two-query loading   | parent query + count query + one child query                       |
| Two lazy product collections | parent query + count query + two child queries per page element    |

Collection entity graphs and collection join fetches behave differently. Hibernate logs:

```text
HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory
```

Their main SQL query does not contain database-level pagination. Hibernate loads the complete joined result, reconstructs and deduplicates the parent entities, and only then returns the requested page. A smaller page response therefore does not necessarily reduce the main query's database, network, or memory cost.

## Conclusions

- The observed runtime query counts match `QueryBehaviorIntegrationTest`.
- `/author/no-transaction` intentionally demonstrates why lazy collections cannot be accessed after the persistence session closes.
- Transactional lazy loading avoids the exception but introduces N+1 queries.
- Fetch joins and entity graphs minimize query count, but collection fetches combined with pagination are unsafe for large result sets because pagination happens in memory.
- Collection join-fetch count queries must count distinct parent IDs to avoid incorrect page metadata.
- Batch fetching is a useful compromise.
- Explicit two-query loading provides the most predictable behavior here: two queries, correct parent pagination, and no Cartesian row multiplication.

Because `size=20` exceeds every dataset's total row count, Spring Data did not need to execute separate count queries during this run.
